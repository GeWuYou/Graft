# 运行目标与基础设施信息架构设计

## 1. 目的与 Authority

本设计定义 Runtime Target、Infrastructure Provider 菜单与共享基础设施资源的长期边界。导航展示以 `导航与资源路由信息架构规范.md` 为权威；Application 与 Compose 生命周期以 `Compose项目管理设计.md` 为权威；Docker Container 资源以 `容器管理设计.md` 为权威。

## 2. 对象边界

- `Runtime Target` 是连接、认证引用、Provider、显示名称、标签、连通性和 capability discovery 的唯一 authority。
- `Runtime Provider` 是 Target 的类型。Docker、Kubernetes、Podman Provider 页面只消费对应 Target，不能维护第二套连接目录。
- `Application` 是业务入口。Compose Project 是 Application/Project 的部署与生命周期 authority，Container 是运行时事实 authority。
- `Registry`、`Certificates` 等跨 Target 使用的对象是共享基础设施资源；Provider 页面只能展示关联和跳转。

首期 Target 模型必须至少表达稳定标识、显示名称、Provider、连接方式、凭据引用、可见性/授权范围、连通性状态与发现到的 capabilities。凭据内容不得出现在列表、详情、日志、审计 metadata 或前端状态中。

运行目标列表采用 `limit` / `offset` 分页，首期只接受 10、20、50、100 条窗口，默认 10。Docker Target 列表项还返回目标级摘要：容器总数/运行数/停止数、镜像总数/使用数/未使用数、运行中容器的 CPU 与内存聚合、以及 Docker Root Dir 所在文件系统的磁盘用量。每一项独立声明可用性与不可用原因，采集失败不得伪造零值；服务端可在进程内短暂缓存该摘要，但显式刷新或发现必须使缓存失效。

`Local Docker` 是 system-managed Docker Target。启动与显式发现均探测本机 Unix socket：从未发现过且 socket 不存在时不创建记录；socket 存在但不能连接 daemon 时创建或更新不可用记录；已经发现过的记录在 socket 消失或 daemon 故障时保留为不可用，以便用户在安装或修复 Docker 后通过显式发现恢复。存活 Target 的展示名称按去空白、大小写不敏感规则唯一。

Application 列表只持久化 `runtime_target_id` 引用，并通过 `server/internal/moduleapi.RuntimeTargetReader` 消费 `{id, display_name, provider}` 摘要。Project 不得直查 `runtime_targets`，也不得复制 endpoint、credential 或 provider registry。当前只有 `application_type=compose` 与 `provider=docker`；未来 Target/Provider 只有在其应用适配器存在后才能成为可创建的 Application。

## 3. 导航与可见性

保持当前侧栏模式。Infrastructure 下的 `运行目标`、共享资源菜单和 Provider 菜单都是普通同级菜单；`共享资源` 与 `运行时` 仅是 Section Label，不能成为 route、permission、breadcrumb、Tab、quick action 或菜单节点。

- Docker 在至少一个 Docker Target 已登记且容器 capability 可用时显示。
- Kubernetes、Podman 的同名菜单分别在至少一个对应 Target 已登记且具有真实 capability 时显示。
- 没有可见子菜单的 Section Label 不渲染；禁止空 Provider 入口和“即将推出”菜单。
- Docker 页通过页面内资源导航承载 Containers、Images、Networks、Volumes、System；Swarm 只在对应能力已发现时出现。

## 4. 安全与连接

Docker Target 支持本地 Unix socket 和 mTLS TCP。明文 TCP 不得保存、测试或使用。私钥、证书和 Registry 凭据必须通过加密凭据引用管理；运行时 API 只可返回脱敏引用和状态。

所有资源查询和操作都必须受 Target 授权范围约束。多 Target 聚合是服务端查询语义，不能依靠前端合并越过授权。

## 5. 演进顺序

1. 建立 Section Label 菜单契约与侧栏渲染，保持既有导航模式。
2. 建立 Runtime Target、连接测试、凭据引用与 Docker capability discovery。
3. 将 Docker Containers 收敛为 `deployment_type`、`runtime_target` 与 nullable `application_id`；删除“来源”这一混合语义。
4. 增加 Docker Images、Networks、Volumes、System，并从 Application/Compose 提供关联资源跳转。
5. 仅在具备 Target 与 capability 后，为 Kubernetes、Podman 和共享资源逐项扩展。
