# Graft Task Runtime 设计

## 1. 定位

`server/modules/task` 是平台级、module-owned 的 Task Runtime。它管理持久化任务的状态机、阶段执行、恢复判断、日志、少量非可推导事件、查询 API 和 realtime 发布。它不是通用 Job Queue，不是 `scheduler` 的替代品，也不是 Temporal Server 的缩写实现。

产品和开发术语固定为：`Task`、`TaskPlan`、`Stage`、`StageExecutor`。不得把 `Workflow`、`Activity` 作为 Task Runtime 的公开领域模型，以免与将来的自动化流程、CI 或产品流程混淆。

## 2. Authority 与边界

| Owner | 负责 | 不负责 |
| --- | --- | --- |
| `task` module | Task/Stage 状态机、持久化、worker、retry/cancel、日志、event、`task:{id}` realtime、通用查询 | Compose、镜像、迁移、备份等业务动作语义 |
| 业务 module | 生成冻结的 `TaskPlan`、注册 `StageExecutor`、验证业务前置条件、执行业务副作用、资源级授权策略 | 自建 task 表、runner、日志表或 WebSocket topic |
| `scheduler` module | 在预定时间提交一个 Task | 领取或执行 Stage |
| `container` module | 容器 runtime 和 health 原始事实 | Task 生命周期、Compose 命令输出 |
| core | DB、DI、认证、realtime Hub 等基础设施 | Task 业务状态机 |

依赖方向只能是业务 module -> `task` 的 `moduleapi` capability。`task` 不得 import 或注册 `project`、`image`、`migration`、`backup` 的实现。

## 3. 执行模型

```text
业务入口或 scheduler
  -> TaskService.Submit(TaskPlan)
  -> Task + Stages 持久化
  -> dispatcher 领取下一 pending Stage
  -> StageExecutor.Execute(StageRun)
  -> 状态、日志、必要 event 先落 PostgreSQL
  -> 发布 realtime 增量
```

`TaskPlan` 在提交时冻结：task type、owner、阶段顺序、executor type、脱敏输入、retry 与 recovery policy 都成为该次 Task 的事实。运行中配置变更不会改写已经提交的计划。

MVP 只支持串行 Stage。`TaskPlan` 不包含 DAG、分支、join、child task、signal 或可执行 DSL；这些需求在未来证明必要前不得进入模型。

## 4. 状态机

Task 状态：

```text
pending -> scheduled -> running -> success
                       |           -> failed
                       |           -> cancelled
                       -> needs_attention
```

`scheduled` 用于已有 `scheduled_at` 但尚不可领取的 Task；即时 API 提交从 `pending` 开始。取消请求在持久化 `cancel_requested_at` 后由 runner 协作完成，不能假定外部副作用已回滚。

Stage 状态：

```text
pending -> running -> success | failed | skipped | cancelled | unknown
```

只有当前 Stage 可运行。Task Runtime 计算当前 Stage 与可推导的阶段时间线；业务 executor 不得直接写 Task/Stage 状态。

### 崩溃恢复

PostgreSQL 中 `pending` 和 `scheduled` Stage 在 module restart 后可重新领取。进程崩溃时仍为 `running` 的 Stage 不能被猜测为成功或失败：Runtime 将其标为 `unknown`，将 Task 标为 `needs_attention`，并追加 `recovery_required` event。

默认 recovery policy 为 `manual_reconcile`。特别是 `docker compose pull/build/up/down`，不可自动重跑 shell；操作者确认外部实际状态后，才能使用 capability 允许的 retry 创建新 attempt。只有业务 module 明确声明幂等且可自动重试的 Stage 才能被 Runtime 延迟 retry。

## 5. Executor 和注册

稳定跨模块接口定义在 `server/internal/moduleapi/task.go`：

```go
type StageExecutor interface {
    Type() StageExecutorType
    Execute(ctx context.Context, run StageRun) error
    Cancel(ctx context.Context, run StageRun) error
}
```

业务 module 在 `Register` 期通过 `TaskRuntimeRegistrar` 注册 executor 和 owner authorizer；`task.Boot` 才启动 dispatcher/worker，确保所有 executor 已注册。`StageRun` 仅暴露本次 Stage 的冻结输入、attempt、cancel 状态和受控日志写入，避免 executor 越过 Runtime 修改状态。

Runtime 在持久化前验证 plan 的 Stage key/sequence、retry/recovery policy 和已注册 executor type；任何未知 executor 或无效 plan 都必须在 Task 创建前被拒绝。

示例：Project 生成 `project.compose.redeploy` 的 plan，依序使用 `project.compose.down`、`project.compose.pull`、`project.compose.build`、`project.compose.up`、`project.compose.health-check`、`project.compose.status-sync` executor；Task Runtime 不理解这些名称。

## 6. 持久化模型

PostgreSQL 是唯一事实来源。未来 migration 由 `task` module 持有，并遵循 table/migration governance。

| Table | 事实 | 关键字段与约束 |
| --- | --- | --- |
| `tasks` | 一次 Task execution | `task_type`、`owner_type/id`、`status`、`input_json`、`plan_json`、`state_json`、current stage、requester、timestamps、failure/cancel 信息；active owner 部分唯一索引 |
| `task_stages` | 每个冻结 Stage 及其 attempt | `task_id`、key、sequence、executor type、status、attempt/max attempts、retry time、recovery policy、result/error、timestamps；`(task_id, sequence)` 唯一 |
| `task_events` | 不可由 Task/Stage 行推导的事实 | task created、cancel requested/cancelled、retry requested/scheduled、recovery required/resolved；`(task_id, sequence)` 唯一 |
| `task_logs` | Stage 输出和系统诊断 | task/stage、sequence、stdout/stderr/system、level、line、occurred_at；`(task_id, sequence)` 唯一 |

Stage started/completed/failed 不重复写 `task_events`，因为 `task_stages` 是这类 lifecycle 的 authority。日志逐行（或受限批次）写入，单行和单 Task 容量必须有上限；display command、input 和日志均需脱敏。

新表默认具备标准 audit fields、`deleted_at BIGINT NOT NULL DEFAULT 0` 与 live query `deleted_at = 0`。执行历史的业务删除不属于 MVP；保留/归档策略以后显式设计。

## 7. Worker、并发与 Redis

MVP 使用 DB-backed dispatcher 和 module 内固定 worker pool。worker 用事务和 `FOR UPDATE SKIP LOCKED` 领取可执行 Stage；全局并发由配置的 worker 数限制，每 owner 的 active Task 由数据库部分唯一索引限制。

Redis 不在正确性路径：不保存 Task/Stage/History/Log，不作为队列或唯一锁。MVP 轮询 PostgreSQL，允许进程内 channel 降低同进程唤醒延迟。未来 Redis 只能作为 best-effort wakeup、cache 或 realtime fanout，仍不得替代 PostgreSQL 的领取或状态转换。

## 8. API、授权与 realtime

通用 HTTP contract 由 `openapi/**` 持有：`/api/tasks`、Task detail、stages、events、logs、cancel 与 stage retry。业务 API 保持业务语义，例如 Project 的 redeploy route 仅完成 Project 权限/guard 后提交 Task，最终迁移为 `202 Accepted` 和 Task receipt。

Task API 通过 owner authorizer 在每次 list/detail/log/event/cancel/retry 重新检查资源权限；不能仅以可枚举 task ID 或全局 task permission 授权。Task detail 返回显式 `capabilities`，例如 `cancel`、`retry`、`download_log`，前端不得自行根据 status 猜测。

统一 realtime topic 为 `task:{id}`。Task module 只在成功持久化后发布 `task.created`、`task.started`、`task.stage.started`、`task.stage.completed`、`task.log.appended`、`task.completed`、`task.failed` 等增量。HTTP snapshot/events/logs 是断线回放 authority；WebSocket 不是唯一事实来源。

## 9. 前端边界

`web/src/modules/task/**` 将拥有可嵌入的 `TaskDetailDrawer` 和历史列表，展示 type、owner、status、current stage、stage timeline、logs、error、capabilities。Project 只提交 Task 并打开这一通用 UI；不得创建仅 Compose 可用的 Deployment Drawer。

## 10. MVP 与非目标

MVP：串行 plan、持久化 Task/Stage/log/event、in-process worker、取消、受控 retry、unknown/needs_attention 恢复、通用 API/realtime/UI、Project 首个接入。

非目标：MQ、Temporal Server、分布式 worker、自动续跑未知 Docker 命令、DAG、精确 Docker layer 百分比、通用远程执行平台。
