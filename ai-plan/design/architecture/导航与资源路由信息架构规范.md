# Graft 导航与资源路由信息架构规范

## 1. 目的与权威边界

Graft 是自托管应用平台。Application 以业务资产组织；Infrastructure 可以把已登记、可用的 Runtime Provider 作为普通菜单，以承接该 Provider 的运行时资源。本规范是 Web 导航、UI route、全局入口和对象详情能力的仓库级设计权威；模块 descriptor、菜单 bootstrap 和 web 路由装配必须以它为分类依据。

导航和可见 UI URL 都是产品 IA 的组成部分。可见菜单项的 canonical UI URL 必须以所属一级导航领域为前缀；看到 URL 应能直接判断用户所在领域。新增 Runtime Provider 或创建来源不得改变该领域前缀。

本规范只约束用户可见 UI URL；HTTP API endpoint 的路径由服务端 API 边界治理单独决定，不在本次迁移范围内。

## 2. 导航分类法

一级导航只表示以下领域。分组无授权可见子项时不得渲染，因此 Build 与 Resources 虽为正式领域，当前可以隐藏。

| 领域 | 管理对象 | 示例 |
| --- | --- | --- |
| Application | 用户交付、部署或运行的业务资产 | Projects、Templates、Releases、Catalog |
| Infrastructure | 应用运行所在的平台与环境 | Hosts、Containers、Clusters、Networks、Storage |
| Build | 应用生成过程 | Build Jobs、Image Builds、Artifacts、Cache |
| Resources | 可被多个对象引用、但自身不运行的共享依赖 | Credentials、Registries、Secrets、Config、Template Repositories |
| Observability | 运行数据和统一分析 | Logs、Metrics、Alerts、Traces、Events、Platform diagnostics |
| Security | 平台身份、授权和安全留痕 | Users、Roles、Permissions、Tokens、Audit |
| Platform | Graft 自身的管理能力 | Settings、Automation、Announcements、Plugins、License |

二级菜单必须是用户会主动寻找的业务对象或平台能力。Docker、Kubernetes 与 Podman 是已登记 Runtime Target 的 Provider 菜单例外：它们只属于 Infrastructure，且只在至少一个相同 Provider 的 Target 已登记并报告真实能力时可见。Compose 仍是 Application 中 Project 的部署生命周期，不得成为 Infrastructure Runtime 菜单。containerd、Nomad、OCI、Helm、Git、SSH、Workspace、Authority 与 Snapshot 不得成为菜单领域或菜单名称。

### 2.1 基础设施 Section Label

Infrastructure 保持既有侧栏导航模式，不引入 Workspace Mode，也不得因选择 Runtime Target 替换整套侧栏。它可使用仅视觉用途的 Section Label，示例：

```text
基础设施
共享资源
  镜像仓库
  Certificates

运行目标

运行时
  Docker
  Kubernetes
  Podman
```

`共享资源` 与 `运行时` 是不可点击的文本分组，不是菜单节点：没有 UI route、权限、Tab、breadcrumb、quick action、菜单 code 或菜单身份；当其下没有授权且可用的普通菜单时不得渲染。`镜像仓库`、`Certificates`、`运行目标`、Docker、Kubernetes 与 Podman 仍是 Infrastructure 下的普通同级菜单。共享资源分组固定显示在运行目标之前；Provider 可在运行时视觉分组下拥有一个无路由的技术分组和稳定资源叶子；当前 Docker 固定为 `Docker > 容器、镜像、数据卷`，Docker 本身没有 UI route、权限或独立页面。

### 2.2 菜单图标语义门

菜单图标是导航契约的一部分，不是页面装饰。新增、替换或评审菜单图标时，必须先完成以下判断，并把结果落实在后端菜单声明的语义键中：

1. 明确用户主动管理的对象或平台能力：领域、资源、对象能力、运行状态和 Provider 不得混为一谈。
2. 用一句话描述图标应表达的业务语义，例如“可复用的应用蓝图目录”“持久化存储挂载”“HTTP 请求性能”，不得只写“一个好看的图标”或“一个 chart”。
3. 检查父级、相邻菜单和同类资源，避免父子重复、同级撞义和同一图形承担多个业务含义。
4. 优先选择跨 Provider 稳定的业务语义；Docker、Compose、Kubernetes、Git 等只在 Provider 分组或明确的实现属性位置使用。
5. 非可点击的 Section Label 不拥有图标；菜单外全局入口不通过侧边栏图标补成菜单节点。
6. 图标必须在折叠侧边栏、浅色/深色主题和 16 至 20px 尺寸下仍可区分；颜色不能成为唯一语义。

以下选择必须拒绝：仅因图形好看而选择、用文件夹代表模板、用数据库代表所有存储或依赖、用服务器代表所有基础设施、用搜索代表所有日志、用钥匙代表所有权限、用铃铛代表所有公告和通知。

图标 authority 仍在服务端菜单声明；`web/src/shared/icons` 只负责静态渲染映射。新增服务端语义键必须同步加入 web resolver 和覆盖测试；未知键可以保留异常保护 fallback，但仓库声明的菜单不得依赖 fallback。

## 3. Runtime、Source 与对象能力

- Application 是唯一业务入口：Project 可以有 Compose 或未来部署方式，但仍属于 Application。创建严格按 `Deployment Type -> Runtime Target -> Application Source` 进行：Compose 是基于 Compose Specification 的 Deployment Type，Docker、Podman、containerd 是 Runtime Provider，不得出现 `Docker Compose` / `Podman Compose` 两个一级模型。Compose Project 拥有 `up`、`down`、`restart`、`redeploy` 等部署生命周期 authority，不得迁入 Docker 菜单。
- Runtime Target 是连接与能力发现的 authority；Docker、Kubernetes、Podman 页面只消费匹配 Target，绝不维护第二套连接目录。Runtime Provider 既是 Target 的属性，也可以在满足 2.1 可见性条件时作为 Infrastructure 菜单。
- Registry、Certificates 等被多个 Target 或构建流程引用的对象，属于 Infrastructure 内“共享资源”视觉分组；Provider 页面只显示关联和跳转，不复制其管理 authority。
- Source 是已选择 Deployment Type 与 Runtime Target 后的创建管道，而非对象类别：Blank、Template、Git Repository、Import Existing、ZIP、OCI 与 Remote Host 都是 `Project Source`，不得产生 `Git Project` 或 `Compose Project` 这类菜单。尚未实现的 Git 可在 Source 页面仅以禁用卡片加本地化“暂不支持”提示表达路线图；它不得拥有 URL、API、创建方式枚举、持久化来源类型或占位页面。Remote 与 ZIP 不显示入口。
- Template 是具有独立创建、编辑、版本、发布生命周期的可交付资产时进入 Application。当前 Template 同时作为 Project 创建来源和 Application 下的可见管理资源；Template Repository 属于 Resources。
- Terminal、Files、Logs、Exec、Shell 与 Console 都是对象能力，必须依附 Host、Project 或 Container detail，不能成为一级菜单。
- Notification Center 是菜单外的全局入口，不能从 Platform 或 Observability 菜单派生。

### 3.1 Runtime Target Summary 与 Provider 扩展

Runtime Target 页面是运行目标总览，而不是任一 Provider 的对象总览。列表与对象详情必须先消费同一份 provider-neutral `Runtime Summary`：运行目标身份（名称、runtime type、provider）、连接（endpoint 与连接方式）、版本、健康状态、最后同步时间，以及资源概览（workloads、CPU、内存、存储）。

- `workloads` 是运行单元的通用计数：Docker 映射为 Container，Kubernetes 映射为 Pod，Nomad 映射为 Allocation，Systemd 映射为 Service；公共契约不得使用 `containers` 作为字段或页面主列。
- CPU、内存、存储等资源指标可各自不可用；可用性不足不得把一个可连接 Target 误报为不健康。健康状态只回答 Provider 连接及其基本能力是否可用。
- Image、Volume、Network、Namespace、Deployment 等不是公共资源字段。它们只能作为 `providerDetails` 的具名、类型化扩展，由 Provider 真实采集后返回；不得以任意 map、服务端组件名或前端动态 UI 元数据替代稳定类型边界。
- Docker 扩展可报告真实的 images、volumes、networks 与 Docker 版本信息；它们不能反向定义 Runtime Summary 的页面结构或 API 形状。
- Kubernetes、Podman、Nomad 等只有在已登记对应 Target 且该 Target 报告真实 capability 后，才能新增自己的 Provider 详情、资源叶子或菜单入口。不得为尚未实现的 Provider 创建占位页、占位菜单、占位 API 或伪造空统计。

因此 Runtime Target 的列表用于跨 Target 比较，`/infrastructure/runtime-targets/:id` 是该 Target 的对象详情：先呈现 Runtime Summary，再呈现匹配 Provider 的真实扩展。Provider 资源页仍由 Provider 自己拥有，不从 Runtime Target 详情派生新的通用资源抽象。

## 4. UI 路由规则

可见菜单的 UI URL 必须镜像 IA：`/<domain>/<resource>`，详情、创建与页面内对象能力继承该资源前缀。领域 slug 固定为 `applications`、`infrastructure`、`build`、`resources`、`observability`、`security`、`platform`。例如 Project 使用 `/applications/projects/**`，而不是 `/compose/projects/**` 或 `/git-projects/**`。创建的 canonical 路径依次为 `/applications/projects/create`（Deployment Type）、`/applications/projects/create/target?deployment=compose`（Runtime Target）、`/applications/projects/create/source?deployment=compose&runtime_target_id=<target-id>`（Source）及其 `blank`、`template`、`import` 向导。`runtime_target_id` 指既有运行目标，不能误用创建成功后才存在的 Application ID。Docker、Kubernetes、Compose、Git 等技术或创建来源默认不得成为 URL 层级；Docker 容器管理是已批准的例外，使用 `/infrastructure/docker/containers/**` 镜像其无路由父分组。Docker 镜像管理使用稳定资源 URL `/infrastructure/images`，只在菜单树中归入 Docker，不将 Docker 加入该 URL 层级。

一级导航 group 仍是图节点，不拥有自身 UI route；仅可见 entry 拥有 canonical URL。Notification Center、首页和认证等菜单外全局页可以使用不带领域前缀的专属 URL。HTTP API 继续按领域资源组织，UI IA 不得强行改写 API endpoint。

分页列表的快捷筛选由无菜单的 `saved-view` module 提供持久化能力。它不是导航对象、菜单、权限或通用 HTTP 入口；每个消费模块必须在自己的已授权 API route 上校验 surface 与筛选语义，且视图始终按用户私有隔离。

迁移 UI route 时不得保留旧路径 alias、redirect 或兼容菜单节点。若必须例外，必须先按根 `AGENTS.md` 的 compatibility 例外规则记录 authority、原因、消费者、清理触发条件和验证范围。

## 5. 当前映射

| 当前能力 | 导航归属 | Canonical UI URL | 说明 |
| --- | --- | --- | --- |
| Projects、部署模型、运行目标与创建来源 | Application > Projects | `/applications/projects/**` | `/create` 先选择 Deployment Type，再选择 Runtime Target，最后选择 Source；Compose 生命周期仍在 Project |
| Templates | Application > Templates | `/applications/templates`, `/applications/templates/create`, `/applications/templates/:templateId` | 模板草稿、发布版本和归档由 Application Template 管理能力拥有；`/create` 是菜单外三步创建工作流，Template 作为 Application 创建来源时使用 `/applications/create/template` |
| Runtime Targets | Infrastructure > Runtime Targets | `/infrastructure/runtime-targets`, `/infrastructure/runtime-targets/:id` | 连接、健康与通用资源概览；详情先显示 Runtime Summary，再显示真实 Provider 扩展 |
| Docker Containers 与详情能力 | Infrastructure > Runtime（Section Label）> Docker > Containers | `/infrastructure/docker/containers/**` | Docker Provider 自有资源页；Container 不定义通用 Runtime 资源模型，Terminal/Files 等留在 detail |
| Docker Image Management | Infrastructure > Runtime（Section Label）> Docker > Image Management | `/infrastructure/images` | Docker Provider 自有镜像资源页；支持拉取、打标签和单镜像删除，不引入 registry、构建或 prune authority |
| Docker Volume Management | Infrastructure > Runtime（Section Label）> Docker > Volumes | `/infrastructure/docker/volumes` | Docker Provider 自有数据卷资源页；支持查看、详情和受权限保护的数据卷删除 |
| Registry | Infrastructure > Shared resources（位于 Runtime Targets 之前） | `/infrastructure/registries` | 跨 Target 共享的镜像仓库管理；不是 Docker 私有资源 |
| Certificates | Infrastructure > Shared resources（位于 Runtime Targets 之前） | future stable resource URLs | 跨 Target 共享；不是 Docker 私有资源 |
| Graft Platform Instance diagnostics | Observability > Overview / Service Status / Dependencies / Modules | `/observability/overview`, `/observability/service-status`, `/observability/dependencies`, `/observability/modules` | 不是 Host 或 OS 管理；服务状态展示进程、Go Runtime、依赖与服务器环境 |
| Security overview | Security | `/security/overview` | 统一聚合访问控制态势与审计风险；不保留旧概览别名 |
| Users | Security > Access Control (Section Label) > Users | `/security/users` | 安全域用户管理入口 |
| Roles | Security > Access Control (Section Label) > Roles | `/security/roles` | 安全域角色管理入口 |
| Permissions | Security > Access Control (Section Label) > Permissions | `/security/permissions` | 安全域权限管理入口 |
| Audit logs | Security > Audit | `/security/audit/**` | Audit 为安全留痕与证据钻取；排序位于 Access Control 之前 |
| Access and application logs | Observability > Logs | `/observability/access-logs/**`, `/observability/application-logs/**` | 统一分析入口 |
| Scheduled tasks | Platform > Automation | `/platform/scheduled-tasks` | 平台自动化能力 |
| System configuration | Platform > System configuration | `/platform/system-config` | 平台自身配置 |
| Platform connectivity and outbound network policy | Platform > Network | `/platform/network` | `platform-network` 的唯一管理入口；根页面展示平台出站连通性健康检查，并可进入 `/platform/network/outbound` 管理 Graft server 主动 HTTP(S) 的代理与 NO_PROXY 策略。该能力不管理 Docker daemon image pull proxy，也不作为通用 System Config 页面中的配置对象展示 |
| Announcements | Platform > Notifications | `/platform/announcements` | 平台通知管理 |
| Notification Center | Global entry | `/notifications` | 不进入可见菜单树 |

## 6. 新功能决策门

新增或移动功能前必须回答：用户真正管理的对象是什么；它是否共享资源；它是否只是对象能力；Runtime Provider 是否已有可用 Target 与真实 capability；以及它所属的 IA domain 与 `/<domain>/<resource>` URL。无法确定对象、领域、父节点或稳定资源边界时，必须在注册菜单、UI route、alias、redirect 或占位页之前停止，并请求产品决策。`graft-navigation-route-governance` 是该门的执行技能。

菜单图标变更还必须附带：当前语义、目标语义、与父级及相邻菜单的差异说明、折叠态/主题态验收范围，以及服务端语义键和 web resolver 的覆盖结果。图标变更不得作为绕过上游菜单 authority 的页面局部映射。
