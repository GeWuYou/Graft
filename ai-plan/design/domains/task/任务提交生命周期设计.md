# Task Submission 生命周期设计

## 1. Authority

`server/modules/task` 拥有 `TaskSubmission` 聚合与 Task 执行运行时。`server/modules/build` 作为首个前置条件写入方，只实现通用的 Submission writer；OpenAPI 是任务状态的跨端 wire contract authority。

## 2. 两条状态机

```text
TaskSubmission: reserved -> activated | discarded | expired
Task: scheduled -> ready -> running -> success | failed | cancelled | needs_attention
```

`activated`、`discarded` 与 `expired` 都是 Submission 终态。Task 仅在本地前置条件已经持久化的原子事务中创建；因此 Worker 的入口只读取 `TaskStatusReady`，后续同一 Task 的串行 Stage 可由 `running` Task 继续领取，Worker 不查询 Submission、lease 或快照。

## 3. Submission 聚合

`task_submissions` 是一等持久化事实，持有 stable submission ID、owner、task type、幂等键摘要、冻结 fingerprint、状态、统一 `submission_version`、lease 到期时间、绝对 deadline、前置条件引用和可空 Task ID。

`submission_version` 是所有变更的 fencing token。续租、丢弃、到期和物化都必须以 `id + state + submission_version` 进行 CAS；成功写入后版本递增。lease token 仅作为授权 handle 的秘密证明，数据库只保存其摘要。

每个 TaskType 在注册时声明 `SubmissionPolicy`：lease TTL、绝对 deadline、续租窗口与前置条件类型。Runtime 施加全局上限，并在创建时冻结解析后的 policy；长时间计算必须发生在获取 lease 前。

## 4. Owner 互斥

不引入持久 owner slot/claim 表。`task_submissions` 对 `state='reserved'` 建立局部唯一索引，`tasks` 保留覆盖 `ready`、`scheduled`、`running` 和 `needs_attention` 的活跃 owner 局部唯一索引；两张表仍是唯一业务事实。

跨表互斥由 PostgreSQL transaction advisory lock 保证。所有获取、物化、过期、丢弃、普通提交和 Task 终态的 owner-capacity 写路径，均按稳定 `(owner_type, owner_id)` 64 位键先获取同一事务锁，再检查对侧事实表并写入自身。锁顺序固定为 owner advisory lock 后 Submission/Task 行锁，避免死锁。该锁是关系型并发协议，不保存状态，也不需要 drift reconciler。

## 5. Materialize Contract

Task Runtime 只定义通用 `Materialize(ctx, submission, writer)` 协议；不引用 Build、Docker、OCI、Git 或 Helm 类型。调用方提供受事务限制的 writer，在同一 PostgreSQL 事务内写入其前置条件事实。

本地实现顺序为：获取 owner advisory lock 并锁定 Submission -> 验证版本与 lease、检查无活跃 Task -> Runtime 在事务内创建未提交的 `ready` 或 `scheduled` Task/Stage 和 created event -> writer 使用该未提交 Task ID 写 Snapshot -> Submission 变为 activated 并绑定 Task -> commit。事务外不可观察中间状态。

事务提交后才唤醒 Worker；唤醒或 realtime 发布失败不会影响正确性，Worker 的轮询与调度器会补偿。

未来跨数据库或外部前置条件仍复用同一协议，但应在后续 ADR 中以 Outbox/Saga writer 实现其交付与不确定结果处置；不得把本地原子路径重新拆成 `activation_pending`。

## 6. Recovery、Cleanup 与审计

Startup Recovery 与 Periodic Expirer 扫描已到期的 `reserved` Submission，以数据库时钟、行锁和 CAS 将其置为 `expired` 并删除 claim。显式 Discard 只允许 `reserved -> discarded`。两个操作不删除历史记录。

本地原子物化要么完整提交为 `activated + Task`，要么整体回滚为 `reserved`，因此没有 Activation Reconciler 或永久 pending 窗口。

`task_events` 只记录 Task 实际创建后的生命周期事实。Submission 记录自身终态时间、原因、操作者和版本；管理操作通过既有 Audit 能力审计，不新建第二个 reservation event store。

终态 Submission、Task 与 Snapshot 只能在统一 retention、幂等重放窗口和审计保留条件都满足后一起清理。

## 7. Legacy Migration

现有 `activation_required=true` Task 仅通过 legacy adapter 迁移：发现已持久化 Build Snapshot 时，才关联既有 Task 并使其进入 `ready`；没有 Snapshot 证据的记录在 cutover grace window 到期后过期/取消并释放 claim。部署顺序要求先停止旧 writer 并等待该窗口，再执行一次性迁移，永远不得凭 flag 单独创建或提升 `ready` Task。
