# 平台网络连通性诊断设计

## Status

Accepted for staged implementation. The Network module owns the canonical target registry and probe/report domain;
OpenAPI and `web/src/modules/network` consume that authority in later phases.

## Scope

Target Registry、可扩展 Probe、批量连通性检查、目标诊断和安全的出站路由解释。

## Information Architecture

`Platform > Network` remains the single platform entry and exposes three concerns:

```text
Platform > Network
├── Connectivity                    /platform/network
├── Outbound Policy                 /platform/network/outbound
└── Target Diagnostics              /platform/network/:targetId
```

The diagnostics route is target-addressed. A report ID selects data inside a target page and never becomes the page
identity, so a rerun refreshes the latest report without changing the URL. Batch Connectivity and Target Diagnostics
share one Connectivity domain, target registry, report persistence model, and future Pinia store; batch is a compact
health projection rather than a second diagnostic implementation.

## Target Registry And Probe Contract

Each module declares a stable `ConnectivityTargetDescriptor` with target ID, owning module ID, category, i18n title
key, ordered probe kinds, and features. A registry entry does not contain a caller-controlled URL, credentials, or
other executable secret. Built-in categories are `platform`, `oci`, `git`, `general`, and later `custom`.

Probe kinds are typed but extensible. The initial vocabulary includes DNS, TCP, TLS, Certificate, HTTP, SMTP banner,
SMTP EHLO, LDAP bind, OIDC discovery, Webhook POST, and OCI ping. A `ConnectivityReport` stores an ordered
`ProbeResult[]` envelope rather than fixed DNS/TCP/TLS/HTTP columns. New protocol adapters therefore add a kind and
target capability without requiring a database schema change.

Features describe safely available report affordances: `history`, `export`, `exit_ip`, and `proxy_route`. The UI uses
these declarations to hide unsupported cards. HTTP status is a result of an HTTP probe, not a mandatory target field;
SMTP, LDAP, OCI, and future runtime targets do not pretend to be HTTP targets.

## Report And Security Boundary

Reports are versioned, UTC-normalized, and immutable snapshots containing only target ID, overall status, timings,
sanitized probe summaries/error codes, an optional Route Explanation, and an optional masked Exit-IP disclosure.
They never model raw request/response payloads, headers, credentials, proxy URLs, complete certificates, or full Exit
IP persistence. A future secure, permission-gated live read may reveal a complete Exit IP only to
`platform-network.exit-ip.read`; history and exports remain masked and every reveal is audited.

Custom HTTP(S) targets are stored by Network but are not a general-purpose request facility. They accept only HTTP or
HTTPS URLs on ports 80 and 443, reject embedded credentials, fragments, local/private/link-local/metadata/reserved
addresses, and disable redirects. Before every direct connection the runtime resolves the configured hostname again,
rejects any non-public answer, and dials the validated literal IP rather than a mutable hostname. To keep that proof
valid, custom targets do not execute while an outbound HTTP proxy is enabled; built-in consumers continue to use the
platform policy. This is an intentional conservative boundary until a future proxy-aware pinned-resolution transport
can provide equivalent guarantees.

Route Explanation presents administrator-facing facts instead of a proxy rule graph:

```text
Matched Strategy: Platform Default
Decision: HTTP Proxy
Reason: Host not matched by NO_PROXY
```

For direct traffic the decision is `Direct` and the reason identifies the matched NO_PROXY expression. No Clash-like
nodes, modes, GeoIP data, rules tree, or proxy-software terminology belongs to this product surface.

## User Experience

The Connectivity page is an operational health scan. Its header shows Healthy/Degraded/Failed counts, Last Run,
Success Rate, Average Latency, and Worst target before the target list. Each compact row shows target, reachable
state, protocol/HTTP status when applicable, latency, and last checked time; users can run all, auto-refresh, add or
remove custom targets, and sort by latency, state, or recency. Selecting a row opens that target's diagnostics page.

The Diagnostics page is an evidence-first tool: current status, rerun/export actions, available Probe cards, Timing,
Route Explanation, sanitized Trace, and recent history. It deliberately borrows Clash Party's fast batch-scan
interaction, but uses Graft's restrained TDesign platform language and avoids its proxy-client visual model.

## Extension Path

Future OCI Registry, Git, Webhook, SMTP, LDAP, OIDC, Kubernetes API, and Runtime Target Health modules register
their own descriptors and Probe adapters through `server/internal/moduleapi`. They do not add UI-specific target
branches. Persistence, HTTP APIs, RBAC, custom-target SSRF controls, periodic checks, notifications, and the shared
web ConnectivityStore are phased additions; they must consume this contract instead of creating a parallel batch path.
