# 配置治理与迁移规范

本文档定义 Graft 部署配置的契约、校验、生命周期和升级诊断规则。它补充
[部署配置与运行时策略治理规范](部署配置与运行时策略治理规范.md)：后者决定一个值是否属于部署配置或
System Config；本文档决定部署配置如何被声明、解析、校验和演进。

## 1. Authority 与范围

嵌入 `server` 二进制的、版本化 YAML Configuration Schema 是部署配置生命周期的唯一 canonical owner。
运行时 resolver、`.env` 模板、官方 Compose、CLI、CI 和文档均消费该 Schema，不得另行维护必填项、默认值、
废弃状态或兼容映射。

Schema 只治理进程启动前可决定的部署配置，以及官方 Compose 部署拓扑：环境变量、CLI 覆盖、`.env`、
Compose service/environment/volume/port/label/secret/runtime 参数。它不接管 System Config、数据库持久化策略、
任意用户管理的 Compose 项目或 Web 构建期配置。

每个已发布 Schema 都是完整、不可变的快照，存放在 `server/internal/config/schema/vN.yaml` 并以 `go:embed`
随二进制发布。当前二进制只接受它明确支持的 Schema version；由二进制支持的最新版本是当前版本。

## 2. Schema 契约

顶层至少包含：

```yaml
schema_version: 1
environment:
  - name: GRAFT_DATABASE_URL
    config_key: database.url
    type: string
    required: true
    default: null
    description: PostgreSQL connection string
    introduced: v1.0.0
    deprecated: false
    removed: false
    sensitive: true
compose:
  services: []
changes: []
```

环境项必须声明 `name`、`type`、`required`、`default`、`description`、`introduced`、`deprecated` 和
`removed`。废弃或删除项必须声明 `replacement`（无替代项时显式为 `null`）及诊断严重度。Schema 可为类型
添加 enum、格式、范围和跨字段约束；动态默认值只能引用一个受限的命名解析器，不允许在 YAML 中执行脚本。
`sensitive` 使值和来源细节在所有报告中掩码。

Compose 契约按 service 和 Compose 字段路径声明必需或受限的 `environment`、`env_file`、`volumes`、`ports`、
`labels`、`secrets`、`command`、`entrypoint`、用户和运行时参数。它描述官方部署必须满足的最小拓扑，不能成为
任意 Compose 项目的通用策略引擎。

`changes` 记录当前版本相对上一版本的 `added`、`renamed`、`deprecated`、`removed` 或默认值变化，附带
operator 可读的迁移说明。新增或改变配置时必须先修改 Schema，再同步 consumer、模板、Compose 和测试。

## 3. 解析与校验

单一 resolver 按如下优先级生成最终配置：

```text
CLI --set / command argument > process environment > selected .env > Schema default
```

`--env-file` 优先于 `GRAFT_ENV_FILE`，二者只决定 `.env` 输入文件，不能成为业务配置值的额外优先级。
`.env` 必须只读解析，不能回写进程环境。resolver 为每个最终值保存来源 `cli`、`environment`、`env_file` 或
`default`；敏感值只保留不透明来源和掩码元数据。

校验必须基于最终解析结果，但 `deprecated` 和 `removed` 还要扫描原始 `.env` 和实际环境，以发现被高优先级值
覆盖的遗留键。缺失必填项、类型或约束非法、跨字段约束失败、未知/过低的版本和 error 级 removed 项均为错误；
deprecated 与 warning 级 removed 项为警告。未知键默认只报告 warning，除非 Schema 将命名空间标记为封闭。

官方 `.env` 必须提供 `GRAFT_CONFIG_SCHEMA_VERSION`。缺失、低于当前版本或高于当前二进制支持版本都不能通过
部署校验。版本只表明 operator 配置模板所遵循的 Schema，不是应用或数据库版本。

## 4. 启动、Compose 与 CLI

所有会读取启动配置的命令必须先共享 resolver 和 validator。`graft serve` 必须在创建 runtime、连接数据库、
执行 Atlas migration、初始化模块或监听 HTTP 前完成校验；`graft migrate up` 必须在打开数据库和创建 migration
executor 前完成同样校验。校验失败时打印报告并以非零状态退出。

`graft config validate` 是部署前、CI 与 operator 排障的公开入口。它支持 `.env` 选择、CLI 覆盖、可选 Compose
文件和 `text`、`json`、`patch` 输出。成功时输出 `Configuration valid.` 并返回 `0`；配置 findings 返回 `2`；
解析、I/O 或内部故障返回 `1`。`patch` 只生成可审阅迁移建议，首期绝不写入 `.env` 或 Secret。

Compose 校验使用符合 Compose Specification 的 Go loader，执行 YAML 解析、插值和契约比较，但不依赖 Docker
daemon、Docker socket、数据库或其他运行服务。部署级校验将 Compose 每个受约束 service 的有效 environment
送入同一 resolver，避免 `.env`、Compose 和进程最终值各自得出不同结论。

官方生产 Compose 提供 one-shot `config-validate` gate。`bootstrap`、目录初始化服务和 `server` 必须依赖它成功完成；
因此配置错误不会开始迁移、初始化或 HTTP 服务。Compose 自己的 `${VAR:?}` 插值失败可以更早终止，不能替代
Schema 校验。

## 5. 诊断与演进

Finding 必须有稳定 code、severity、scope、key/path、来源、说明、introduced version、replacement 和迁移建议。
文本错误先列错误、再列警告，使用固定标题 `Configuration Validation Failed`，结尾明确
`Application startup aborted.`；JSON 输出同样字段且不含 secret 值。多个 finding 必须一次性报告，不能只返回
第一个错误。

升级按如下生命周期治理：

1. 新键先在下一版 Schema 声明 `introduced` 与默认/必填状态，并在官方模板和 CI 中覆盖。
2. 重命名先标记旧键为 deprecated，指向 replacement；resolver 不提供 alias、双读或隐式 fallback。
3. 废弃窗口结束后把旧键标记 removed，按风险选择 warning 或 error，并输出删除或迁移建议。
4. 后续版本只保留诊断和 patch 生成；只有经独立设计批准的命令才可实现显式、备份安全的写入式迁移。

这套规则不允许为了通过升级而在下游 consumer 新增 legacy alias。若 canonical Schema、官方模板或 Compose
拓扑有误，必须先修复该 authority。

## 6. CI 与验收

CI 顺序固定为 `Build -> Config Validation -> Migration Test -> Unit Test -> Release`。Config Validation 使用
官方 `compose.env.example` 和 `compose.yml` 运行 daemon-free 校验，证明新增必填项、Schema version 与 Compose
模板完整；只有通过后才进入 migration test。发布流水线复用该门禁。

最小回归覆盖包括来源优先级和 provenance 掩码、Schema 版本连续性、必填/类型/跨字段、废弃/删除、patch 输出、
Compose service 路径和插值错误，以及 `serve` 与 `migrate up` 在校验失败时未创建 runtime、数据库连接或 migration
executor。实施顺序见 [配置治理实施路线](../../../roadmap/配置治理实施路线.md)。
