# 部署配置与运行时策略治理规范

本文档定义 Graft 配置的单一来源边界，供开发者和 AI 在新增、修改或删除环境变量、Compose 参数、System Config 与 Vite 配置前使用。

## 1. Authority

同一语义只能有一个 canonical owner。不得以“System Config 覆盖环境变量”、双读、双写或 fallback 的方式维持两份有效配置。

| 类别 | Owner | 典型内容 |
| --- | --- | --- |
| 部署配置 | 环境变量 / Compose | 密钥、数据库和 Redis 连接、监听地址、镜像、挂载、Provider、Socket、数据目录、TLS、模块启动装配 |
| 核心启动配置 | `server/internal/config` | 进程在 System Config 可用前必须决定的安全、网络和日志初始化参数 |
| 运行时策略 | 模块 `ConfigDefinition` + `system-config` | 管理员可修改的功能开关、权限后的危险操作、默认交互限制、保留策略、采样与展示策略 |
| 前端构建与开发配置 | `VITE_*` / Vite | 构建 base、开发代理、Mock 和本地开发诊断；不承载服务端管理员策略 |

资源缺失不是策略关闭。Socket 未挂载、Provider 不可连接或凭据无效时，模块必须报告 runtime unavailable；不得新增环境开关把该状态伪装为“功能未启用”。

## 2. 新配置决策

新增配置前依次回答：

1. 值是否定义部署拓扑、外部连接、密钥或进程构造？是则使用环境变量 / Compose。
2. 值是否由已启动模块在请求或任务执行时消费，且管理员应能在 Web 修改？是则使用模块注册的 System Config。
3. 值是否仅影响前端构建或本地开发？是则使用 `VITE_*`，并保持在客户端边界。
4. 值是否实际描述外部资源是否可用？使用健康探测、能力状态或错误响应，不创建新的开关。

System Config definition 必须声明 schema、i18n metadata、默认值和 `runtime_apply_mode`。`runtime_hot` 表示下一次有效读取生效；需要重启的部署参数不得注册为 System Config。

## 3. Container Boundary

- Docker runtime provider、endpoint 和 `docker.sock` 挂载属于部署配置。
- `ops.container.runtime.enabled`、Shell、高危操作、日志尾数、编排器动作等级、资源采样与环境展示策略属于 System Config。
- Shell 策略开启仍要求部署层 WebSocket Origin allowlist；缺少 allowlist 时必须拒绝 Shell，而不是放宽 Origin 校验。
- 删除或迁移配置定义时，同时清理其 persisted override；不保留 legacy key alias 或 fallback。

## 3.1 Application Root Directory

- `ops.application.root_directory` 是 Application managed create 的唯一 System Config authority；显示名为 `Application Root Directory` / `应用根目录`，默认值为 `/opt/graft/apps`，由 `project` module 注册并在每次 create/validate 时读取。
- 它是 server container 内可见的绝对根目录。用户输入只能是其下的相对应用目录；服务端负责 join、clean、symlink 边界和可写性校验，不能接受任意绝对工作目录作为 fallback。
- 空字符串是管理员保存的显式关闭状态：managed create 必须报告不可用，不能回退到默认值、仓库目录或用户 home。
- 根目录的宿主机 bind mount、目录预创建和运行用户所有权定义部署拓扑，属于 Compose/环境部署配置；System Config 不得声称一个未挂载或不可写的路径可用。
- 该能力尚未发版，配置键从 `ops.project.managed.root_directory` 收敛为 `ops.application.root_directory` 时不提供 legacy key、alias、双读或迁移 fallback；实现必须只注册、只读取和只展示新 key。

## 3.2 Logging Category Boundary

- `GRAFT_LOG_LEVEL` 是启动时日志阈值，支持 `trace`、`debug`、`info`、`warn`、`error`、`dpanic`、`panic` 和 `fatal`。
- `GRAFT_LOG_CATEGORIES` 是唯一的类别部署配置，不得增加每类别环境变量或 System Config 镜像。它严格解析逗号分隔的
  `category=bool`：格式错误、非法布尔值、重复类别和 logger registry 未知类别都会拒绝启动。
- 类别规则按最长已注册命名空间前缀匹配。`false` 会屏蔽该类别所有日志级别；未配置类别保持既有非 TRACE 阈值行为，
  但其高频 TRACE 默认关闭，只有匹配的 `true` 才启用。
- TRACE 仅影响 process-output diagnostics，不是 App Log persistence、查询或管理员运行时策略。

## 3.3 Deployment Runtime Context

- `GRAFT_DEPLOYMENT_RUNTIME`、`GRAFT_DEPLOYMENT_COMPOSE_ROOT`、`GRAFT_DEPLOYMENT_SERVICE_MANAGER`、`GRAFT_DEPLOYMENT_SERVICE_NAME` 和 `GRAFT_IMAGE_TAG` 都是部署配置；它们不属于 System Config，Web 不得创建第二套可写配置。当前官方 Compose profile 只需要 `GRAFT_DEPLOYMENT_RUNTIME=compose` 和可选的 `GRAFT_DEPLOYMENT_COMPOSE_ROOT`。
- `GRAFT_IMAGE_TAG` 是官方 Compose 唯一的镜像引用和更新策略来源。官方 server、web 及初始化服务都从它组成镜像引用：`latest` 跟随 stable、`beta` 跟随 beta、`vX.Y.Z` 锁定 stable、`vX.Y.Z-beta.N` 锁定 beta。Update 只能从相同频道的官方验证 Release 中选择严格更高的目标，禁止降级与频道切换。
- 对跟随策略，runner 以已验证的明确版本 Tag 和 manifest digest 进行临时拉取与部署校验，但完成后 Compose 仍保留 `latest` 或 `beta`；解析出的 release 与 digest 是运行时状态，不是 `.env` 配置。对锁定策略，runner 只在同频道、严格升版成功后原子更新固定 Tag。不存在旧键兼容、alias、双读或 fallback。
- Deployment Runtime 是唯一允许解释环境变量、Docker labels、config files、bind mounts 和宿主机路径并生成 `DeploymentContext` 的组件。Container 只提供 Docker 原始 inspect facts；Update、Backup、Restore、Compose 管理和 diagnostics 只能消费 `DeploymentContext`，不得自行推导部署信息。
- `GRAFT_DEPLOYMENT_COMPOSE_ROOT` 已设置时拥有最高优先级，必须是非空且 Docker daemon 可见的宿主机绝对路径；显式空值或路径校验失败时必须报告不可执行，不能回退到另一种 runtime 或 Docker 自动发现。只有变量未设置时才允许 Docker 自动发现。
- 变量未设置时，Deployment Runtime 通过 Container 提供的当前 server 原始 Docker inspect facts（Compose labels、config files、bind mounts）生成 host Compose root 候选，并要求具备相应受控操作权限的管理员确认。候选 key 必须是不透明服务端标识；原始 host path 不得作为 Web 请求输入。
- `DeploymentContext` 是不可变 value object。状态读取可取得当前 context；受控操作必须重新发现、验证并 freeze 一个 operation-scoped snapshot。候选 key、路径和选择结果不持久化到 System Config、数据库或其他存储。候选缺失、过期或 Docker runtime facts/fingerprint 不一致时必须阻断操作并要求重新确认。
- 二进制部署通过 `GRAFT_DEPLOYMENT_RUNTIME=binary` 声明；`GRAFT_DEPLOYMENT_SERVICE_MANAGER` 与 `GRAFT_DEPLOYMENT_SERVICE_NAME` 仅描述受支持的服务控制面。不得引入 `GRAFT_DEPLOYMENT_BINARY_PATH`、`GRAFT_DEPLOYMENT_WEB_ROOT` 或 Update 前缀的同义配置来猜测 filesystem layout 或 `ExecStart`。
- Docker daemon 返回的 Linux host path 是 Compose runner 挂载和执行的唯一权威路径。容器内路径、Windows/WSL 映射路径和前端自行推导的路径只能作为展示信息，不能替代该执行路径。

## 3.4 Backup Artifact Root

- `GRAFT_BACKUP_ARTIFACT_ROOT` 是 Backup 模块在 server 容器内唯一可写的工件根目录；其宿主机挂载由 `GRAFT_BACKUP_ARTIFACT_HOST_PATH` 决定，二者属于部署配置，不进入 System Config 或 HTTP 请求。
- 官方 Compose 必须在启动 server 前以 `0700` 初始化根目录，并以 `10001:10001` 授予运行用户。配置快照和数据库导出文件必须以 `0600` 创建，日志、Task 输入和 API 响应不得包含工件路径、内容或数据库连接信息。
- 目录缺失、不可写或数据库导出工具不可用属于 Backup runtime unavailable；不得用功能开关、默认 home 目录或任意调用方路径作为 fallback。
- Compose runner 的输入通过 Docker API inline 传递，完成证据通过带 operation/protocol labels 的保留容器日志返回；server 不得假定自身容器可以直接读写自动发现的宿主 Compose root。

## 4. AI Checklist

- 先搜索现有 `ConfigDefinition`、`SystemConfigResolver`、环境读取和 Compose 注入，确定 authority 后再改 consumer。
- 不为同一策略新增环境变量和 System Config 两套默认值。
- 不让 `web` 推断有效策略或资源可用性。
- 变更 stable config key、默认值或 operator-facing 口径时，同步更新测试、示例文件、部署文档和必要 migration。
