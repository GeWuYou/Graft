# 队列采用与任务异步化治理规范

## 1. 适用范围

本规范统一 `server` 中“是否异步、采用什么能力、由谁拥有事实”的判断。它不授权新增泛化 Queue、Worker、Job、DLQ 或第二套任务状态机。当前唯一可采用的两个异步边界是：

- `server/internal/event`：事实事件的同步接收、best-effort 投递或 PostgreSQL Outbox durable delivery。
- `server/modules/task`：有计划执行过程的 Task/Stage Runtime。

`server/internal/eventbus` 是同步进程内总线，不能当作持久队列；`server/internal/scheduler` 是 cron 触发器，不能当作 Task worker。

## 2. Event 与 Task 选型

### 2.1 使用 internal/event

事件表示已经发生的事实，需要一个或多个消费者解耦处理时使用。例如审计、应用日志或通知 fan-out 可以由业务事实发布事件，再由 handler 幂等消费。

必须遵守：

1. Envelope 只放事件类型、版本、来源、关联 ID 和脱敏 payload，不放审计/通知领域模型。
2. 需要跨重启或不能丢失时使用 `DeliveryDurable`；已有 SQL transaction 时调用 `TransactionalPublisher.PublishTx`。
3. Handler 必须幂等，可承受重复执行；Receipt 只表示接收，不表示处理完成。
4. best-effort 适合允许丢失的低价值通知或进程内延迟降低，不得承载业务正确性。
5. 事件 handler 不得执行无界外部副作用；需要进度、取消、阶段、人工恢复时，事件应触发或通知 Task，而非模拟 Task。

### 2.2 使用 modules/task

Task 表示需要查询和管理的执行过程：Docker Compose、升级 runner、备份/恢复、批量导入导出、远程 API/SSH 或其它不可控时长外部副作用。业务模块拥有 plan、executor、业务授权和副作用语义；Task module 拥有状态、阶段、领取、日志、重试、取消、recovery event 和 realtime。

业务模块必须通过 `server/internal/moduleapi/task.go` 的 `TaskService`/`TaskRuntimeRegistrar` 接入，不能自建 task 表、runner、worker、日志表、WebSocket topic 或 queue channel。Project 的参考实现是 `server/modules/project/module.go:Register` -> `registerProjectTaskExecutors` -> `server/modules/project/task_executor.go:composeStageExecutor.Execute`。

### 2.3 何时两者同时使用

长任务可以同时使用两者，但职责必须分开：

```text
HTTP/Cron/Webhook/MCP -> Service -> TaskService.Submit
                                  \-> same SQL transaction + event.PublishTx (if durable fact notification is needed)
Task StageExecutor -> persist state/log/progress -> event/realtime notification
```

Task 是执行事实的 authority；event 是已提交事实的通知或跨模块消费入口。不要用 event payload 维护“伪进度”，不要用 Task event 表替代 Outbox，不要让 Event handler 直接写 Task 终态而绕过 Runtime。

## 3. 标准 HTTP→Task 流程

1. HTTP handler 完成认证、资源授权、输入校验、幂等键提取和同步前置检查。
2. Service 读取 Repository 事实，生成冻结且脱敏的 `TaskPlan`，明确 owner、executor、Stage 顺序、超时、retry/recovery policy 和 external operation identity。
3. 在一个 SQL transaction 中写入必要的业务事实；若需要 durable event，调用 `PublishTx`。Task submission 必须由 Task Runtime 持有其状态转换，不得在 handler 外偷偷开 goroutine。
4. 返回 `202 Accepted`、Task ID、状态查询 URL、realtime topic 和 capability。OpenAPI canonical source 在 `openapi/**`，生成的 web contract 不是修改入口。
5. Task dispatcher 以 PostgreSQL 事务和 `FOR UPDATE SKIP LOCKED` 领取 Stage；executor 使用 context timeout/cancel，写入受控 Task log 和阶段结果。
6. 成功、失败、取消、unknown 和 needs_attention 都必须可查询。HTTP snapshot/events/logs 是回放 authority，realtime 只是增量通知。

短时 CRUD、只读发现、配置校验和确定性查询保持同步。`server/modules/update/routes.go` 的 status/check 即为同步只读例子；升级执行、Compose 生命周期和备份恢复不应沿用该同步等待模式。

## 4. Task ID、进度、重试、DLQ 与幂等

### 4.1 Task ID 与进度

- Task ID 是公开稳定引用，授权必须每次通过 owner authorizer 重查，不能只凭可枚举 ID 或全局 task permission。
- TaskPlan 提交时冻结；运行中配置变更不能重写已提交计划。
- 进度以当前 Stage、attempt、阶段状态、受控 log 和明确的业务 checkpoint 表达。无法准确测量时返回阶段进度或 unknown，不伪造 Docker layer 百分比。
- 统一 realtime 使用 `task:{id}`；断线恢复读取 Task HTTP snapshot/events/logs。

### 4.2 Retry、unknown 与 DLQ

- retry 只能由 Runtime 按 policy 或授权的人工操作创建新 attempt，保留旧 Stage history；不能覆盖失败记录。
- 只有业务模块证明 executor 幂等且外部操作可安全重放时才允许自动 retry。
- 进程崩溃后仍为 running 的 Stage 应进入 `unknown`/`needs_attention`，尤其是 `docker compose pull/build/up/down`、升级、恢复、SSH 和网络调用。
- 本仓库不新增“DLQ Queue”。失败/unknown 记录、recovery_required event、lease expiry、人工 reconcile 和 permitted retry 共同构成 dead-letter 处置面；应提供查询、告警和保留策略。
- 外部 execution lease 与 receipt 必须绑定冻结的 task/stage/attempt、executor、target/provider/capability、
  protocol、operation identity、payload digest 与 fencing token；同一 Stage attempt 的完全相同 receipt 重放可
  幂等成功，内容不同必须拒绝。外部 Agent 只通过 pull claim 工作，不得自建 queue、retry 或状态机。

### 4.3 幂等键

幂等键至少绑定业务 owner、动作类型和外部 operation identity。HTTP 重试、Webhook 重发、Cron 重叠、Event redelivery、Task retry 和外部 callback 必须得到同一结果或明确冲突。幂等不能用内存 map 充当唯一事实，必须落在受约束的数据库事实或外部 provider 的幂等能力上。

## 5. 事务、外部副作用与安全

数据库事务只覆盖数据库事实：业务表、Task submission 所需事实和 durable event/outbox 可以在同一事务内提交。Docker、文件系统、网络、外部 API、Registry、SSH、Compose、Update runner 和 Backup dump/restore 不与 PostgreSQL 共享原子事务，必须使用稳定 operation identity、receipt、超时、取消、结果核对和补偿/人工恢复。

HTTP、Webhook、MCP 或 scheduler 不得把任意 command、host、path、image、credential 或环境变量直接传给 executor。执行器从已授权 owner 和冻结 plan 生成受限参数；敏感输入不得进入 Task log、Event envelope、审计消息或通知正文。外部 API 必须限制响应大小和重定向/网络范围；SSH 必须记录目标引用而非私钥。

## 6. 日志、审计、通知与统计

- Executor 使用 `StageRun.AppendLog`；不要只写 zap，也不要创建模块私有日志表。日志逐行/批次、有大小上限并脱敏。
- 安全和用户操作审计继续由 `server/modules/audit`/HTTP security audit publisher 负责；Task lifecycle event 不自动等价于审计记录。
- 通知通过 `server/modules/notification/publisher.go` 的 capability。通知是消费结果，不应改变已提交业务事实；需可靠发送时使用 durable event 或已有通知 delivery 语义，不新建 Queue。
- 统计和趋势读取保持查询 authority。重计算、导出、批量工作提交 Task，统计展示读取 Task/业务事实，不把内存计数当作恢复依据。
- 指标至少区分 accepted、queued/pending、running、success、failed、cancelled、unknown、retry、lease expiry、backpressure、handler error 和人工 recovery。

## 7. Scheduler、Webhook、Registry、MCP 与 OpenAPI

- Scheduler/Cron 只负责何时触发：`server/internal/scheduler/runtime_tasks.go:RunOnceWithTrigger` 创建 run；长动作随后提交 Task。不要在 CronRuntime 中复制 Stage worker。
- Webhook 当前没有独立通用实现；新增接收入口必须验签、去重、快速返回，并选择 Event 或 Task。投递有独立状态、重试和人工重放需求时使用 Task owner，不在 handler 中阻塞下游。
- Registry（`server/internal/moduleregistry`、`configregistry`、permission/menu registry）只负责注册和冻结能力。executor/handler 在 module Register 期注册，worker 不动态扫描 Registry。
- MCP 开发工具不是运行时依赖；产品 MCP transport 也不能绕过认证、授权和 Task owner。工具触发长操作仍返回 Task receipt。
- OpenAPI 的异步响应、Task ID、状态、capability、错误和 retry/cancel 语义必须先改 canonical source，再更新生成投影；禁止在 web generated contract 加局部 Queue 兼容层。

## 8. 分级门槛

### P0

- 新增泛化 Queue/Worker、第二套任务状态机或第二个 durable job store。
- 业务提交后再补发 durable event，或让 HTTP/Webhook/MCP 直接执行无界外部副作用。
- 自动重试不可证明幂等的 Docker、Update、Backup/restore、SSH 或网络动作。
- 绕过 Task owner authorization、泄露凭据，或让外部 callback 直接修改 Task 状态。

### P1

- 长任务没有 Task ID、冻结计划、Stage、受控日志、progress、cancel、retry 或 unknown/reconcile 路径。
- Event handler 不幂等，Scheduler 无防重提交，外部请求无 timeout/大小/网络边界。
- 业务模块自建 worker/goroutine 处理本应由 Task Runtime 管理的生命周期。

### P2

- OpenAPI 未表达 `202` 和 Task receipt；缺少 Task/Event/通知/人工恢复指标；缺少 shutdown、lease 和 backpressure 验证。
- 事件、Task 日志、审计、通知之间的敏感字段脱敏规则不完整。

### P3

- 为同步查询、配置注册、Git 操作、开发者 MCP 或可丢失低价值通知增加异步包装。
- 以“队列”作为模糊产品名，未说明事实 owner 和保留/恢复语义。

## 9. Review 清单

审查任何异步化 PR 时，必须回答：

1. 这是 Event 还是 Task，为什么不是另一者？是否复用了现有 boundary？
2. canonical authority、owner、Task ID、OpenAPI 和授权链在哪里？
3. Service/Repository/事务边界是什么？durable event 是否 `PublishTx`？
4. progress、log、retry、cancel、unknown、人工恢复和所谓 DLQ 如何查询？
5. 外部副作用的 timeout、幂等键、receipt、脱敏和网络/文件/command 边界是什么？
6. shutdown、lease expiry、backpressure、重复投递、Cron/Webhook 重放如何验证？
7. 是否修改了任何生成文件、迁移、第二套 Queue/Worker 或无关模块？若是，必须先升级 authority 和范围。

## 10. 外部资源销毁

Docker、Compose、Kubernetes、云资源、文件系统或其它外部 authority 的 remove/destroy/untag 不得在 HTTP 请求内同步等待完成。统一流程为：

1. `POST` action 完成认证、资源授权、确认、输入冻结和 operation identity 生成。
2. Task Runtime 持久化 submission/receipt 后返回 `202 Accepted` 与 canonical enveloped Task receipt。
3. executor 执行外部副作用并记录 succeeded、failed、unknown 或 needs_attention；网络超时、daemon crash 和进程退出不能被推断为成功或失败。
4. 相同 operation identity 的安全重放返回原 Task 或执行 provider 级核对；不得新建模块私有任务表或内存幂等 map。

OpenAPI operation 必须声明 `x-graft-destructive.execution: asynchronous`、`retry.mode: task_receipt`、`result.status: 202`，并保持 `exposure.mcp` 与实际 MCP capability 一致。
