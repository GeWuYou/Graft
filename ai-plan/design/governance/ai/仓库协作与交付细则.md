# 仓库协作与交付细则

本文件是根 [AGENTS.md](../../../../AGENTS.md) 在 Git、共享生成资源、CI/CD 任务中的按需执行细则。只有处理这些操作时读取对应章节；
授权、启动、验证入口与完成判定仍归根文件，不在这里重新定义。修复权限直接使用根 Authorized Work。

## Git 与工作树操作

- 工作树通过 `graft-worktree-manager` acquire/status/closeout/release 管理。默认获取最低编号的干净可复用槽位，
  fetch origin 后从 origin/main 建立唯一任务分支。lease 是本地生命周期事实，不保存恢复内容。
- 分支遵守仓库命名 `<type>/<lowercase-kebab-topic>`，type 为 feature/fix/refactor/docs/chore/build/ci；不创建
  feat 或 wt-* 分支。宿主或用户明确指定的命名约束优先。main-XX 仅为无 upstream 的本地池标记，不发布。
- release 前确认已提交、已验证、干净及 manager closeout；legacy-untracked 分支保持现有 clean-and-integrated
  路径。release 先预览，再确认精确已集成 ref；槽位不是长期 feature ownership。
- 合并或 cherry-pick 需事先记录用户授权的 operation、source ref/commit、target workspace、owned scope、
  before/after validation、rollback、invalidation conditions。命令与记录不一致立即停止。默认开发者在主检出区集成。
- 编号工作树不启动服务、浏览器、Compose 或长驻进程，不执行 DDL/DML/migrate up/atlas migrate apply/replay。
  浏览器跟进归获授权且能独立证明待验收 branch/full HEAD 的主检出区；不得阻塞已验证的 scoped commit。

## 提交、推送与所有权

- `graft-commit` 是唯一 scoped commit 工作流。干净起点产生的任务改动可以提交；原先脏状态只有可证明的任务
  文件/hunk 可以自动提交。无法分离的用户/未知改动保留，并报告具体阻塞。
- 裸 `graft-commit` 的初始 inventory 是用户明确确认的全部可提交项，按独立逻辑切片完成全部清单，最终检查
  git status；不把后到的无关改动纳入。带范围的提交请求遵守其范围。必要相关修复适用根授权规则。
- 每个逻辑完成点应直接验证后提交；不要积攒无关完成切片。提交应独立可理解、可测试。显式请求合批时可合批。
- 逐路径或逐 hunk 暂存并检查 cached diff；不因为文件相关就提交其中用户内容。禁止通过中间提交隐藏验证失败。
- 不制造 wip/update/fix typo、调试快照或混入无关格式化的噪音提交。避免仓库级格式化、整理 import、无关 --fix。
- Conventional Commit 格式为 `<type>(<scope>): <summary>`，scope 必填，标题默认英文。普通提交（非 merge/revert）
  必须有真实多行 body，至少一个 `- ` 条目，以动作动词描述独立改动；不得出现字面量转义换行/制表文本。
- feat 是能力新增，fix 是行为修正，refactor 是非功能重构，perf 是可观察性能改进；docs/test/build/ci/chore/style
  使用本义。纯文档不得用 feat。不要通过 hook 绕过完成标准。
- `graft-push` 先区分增量 PR 推送与新发布：已有 upstream 且对应分支有 open PR 时，按 upstream..HEAD 范围保留
  分支名；否则 fetch origin/main，用完整 origin/main..HEAD 确定发布主题，空范围不重命名/发布。
- 新发布的名称要反映全部本地提交，必要时改本地分支和 upstream；不得自动删除旧远端分支。普通 commit 不因主题
  演进强制改名。推送授权不包含 force-push、合并或任意 GitHub 评论。

## 生成资源与契约闭环

Atlas migration、非 OpenAPI 生成物、lockfile、snapshot 是线性资源。并行修改可能冲突时协调 owner，最终集成基于
真实 source 串行生成和复验，不手拼生成产物。Ent/migration 变更仍须满足 server 生成和完成门槛。

OpenAPI source 和确定性派生产物是同一 task-owned contract closure：任务分支同步 source、bundle、server
binding、runtime embedded bundle 和 web schema，运行 `just generate`、`just openapi-check` 及对应两端完成入口。
不能把 freshness 留到集成。冲突时先合并 canonical source，再重新生成、验证，不手工合并派生代码。

## CI/CD 修改

- PR 与发布分开；server/web 分 job。server lint/build-test 可拆分，但都复用 root/server 同一验证入口和 pinned
  golangci-lint 参数。web-check 复用 bun run check，不建 CI-only 验收标准。
- 快速质量/安全与构建测试轨道可以分离；helper 质量 job 只基于仓库规则阻断。阈值/回归窗口放仓库配置，显示分数
  不作阻断 authority。README/ADR/Contract/OpenAPI/Public API Comment 检查不依赖单一质量工具总分。
- 按 Go/前端缓存依赖，保留有诊断价值的产物。仓库成熟度不足时诚实 smoke，不伪造 full build。报告 job 不替代
  web-check/server-build-test；fork PR 无写权限时仍可上传原始测试产物。
- 发布 build once、复用产物，门禁严于 PR，发布/docs 使用明确 concurrency。不要提前增加无需求的 package 发布。
- 版本 tag 由手动 semantic-release 工作流按 Conventional Commits 规则生成，格式 v${version}。需要 tag 触发
  下游工作流时使用已验证的 PAT_TOKEN，不能依赖 GITHUB_TOKEN。tag 发布先跑 server/web 验证再生成或附加产物。
- Release body 由 git-cliff 生成，不在 YAML 手工维护。SBOM/许可证清单只是 Release 维护附件，不改变发布正文或
  创建新部署/package 目标。CodeQL、secret scanning、Dependabot 针对实际语言依赖；可选 docs/benchmark 独立。

## 许可与换行

根 LICENSE 声明 AGPL-3.0-only，不要求自有文件头。第三方/生成/锁文件不得加入自创声明噪音，保留实际上游义务。
引入依赖与分发物时核验兼容性、attribution/NOTICE，不能引入未声明的 source-available 限制。
`.gitattributes` eol=lf 是真相；建议 Git core.autocrlf=input、core.eol=lf、core.safecrlf=true。
`scripts/check_line_endings.py` 检查 index，由 pre-commit 和 PR blocking job 执行。
