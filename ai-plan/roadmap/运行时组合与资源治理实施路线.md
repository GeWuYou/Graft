# 运行时组合与资源治理实施路线

本路线落实 [运行时组合与资源治理设计](../design/architecture/运行时组合与资源治理设计.md)，以降低长期 Module、Provider、Agent、Task Runtime 与 realtime 的资源泄漏和依赖漂移风险。它不引入动态插件加载或 HMR。

## Phase 0: 现状盘点与边界冻结

- 为现有 Module、Task Runtime、realtime stream、event consumer、cron job、外部 client 建立 creator/owner/disposer 清单。
- 修正文档与测试中无法证明关闭责任的路径。
- 不改变公开 API，不创建通用 scope abstraction。

收益：先消除隐性生命周期耦合。风险：盘点可能发现跨 Module authority drift。

## Phase 1: 生命周期与 cleanup 统一

- 为长期 subscription、observer、ticker、worker、connection 建立 idempotent cleanup 和有界 shutdown 证据。
- 明确同步 EventBus 的长期订阅注销策略；保持 durable dispatcher 的 worker ownership 不变。
- 补充 creator/owner/stop-result 的结构化日志和最小行为测试。

收益：可验证停止、降低 goroutine/subscription/timer 泄漏。风险：错误 shutdown order 可能暴露既有依赖。

## Phase 2: 窄 Resource Scope

- 仅在多个 Module 反复需要管理同类 cancellable resource 时，设计窄的 Module resource 或 subscription scope。
- Scope 只收集 disposer 与生命周期 context，不持有业务 repository、事务、权限或 Task 状态。
- 不实现 Agent -> Task -> Plugin 的全局 Context 树。

收益：减少重复 cleanup 样板代码。风险：抽象过早会把 `module.Context` 变成第二个万能容器。

## Phase 3: Capability 与组合声明

- 扩展 composition unit 的 required/exposed capability、configuration owner、runtime resource 与 cleanup metadata。
- 保持 `module.Spec` 的 compile-time dependency authority 和 `moduleapi` 的 typed boundary；不引入字符串 service lookup 或运行时 dependency solver。
- 为 Provider/Agent 建立 capability-local Ready/Degraded/Unavailable 观察面。

收益：组合可审计，失败可定位。风险：metadata 重复既有 ModuleSpec/contract；必须先确认单一 authority。

## Phase 4: 受控变更评估

- 只在有明确隔离、状态迁移、drain/rollback、持久化事实和运维入口时评估 runtime enable/disable。
- 默认采用 process restart、config reconcile 或 Agent reconnect；不实现 Module/Provider HMR。

收益：避免为假想扩展性增加运行时复杂度。风险：任何动态化都可能破坏 route、permission、Task 与外部资源一致性。
