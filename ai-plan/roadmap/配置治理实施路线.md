# 配置治理实施路线

本路线把 [配置治理与迁移规范](../design/governance/platform/配置治理与迁移规范.md) 与
[ADR-020](../design/decisions/ADR-020-configuration-governance-schema.md) 落实为可分批验收的交付。

## Phase 1: Schema Authority 与 Runtime Preflight

- 建立嵌入的 `v1` YAML Schema、Schema loader 和自校验，收敛现有启动环境变量、默认值和生命周期元数据。
- 实现 source-aware resolver、秘密安全 provenance、完整 finding 聚合与 `graft config validate` 的 text/JSON/patch
  合约及退出码。
- 让 `serve` 与 `migrate up` 在数据库、Atlas migration、runtime、模块和 HTTP 初始化前运行相同 preflight。
- 验收：缺失/非法/版本不兼容配置以 `2` 退出；测试证明受影响初始化对象均未创建。

## Phase 2: Compose Contract 与 Production Gate

- 在 Schema 增加官方 Compose service contract；以 standards-compliant、daemon-free loader 完成插值和拓扑校验。
- 使 `compose.env.example`、`compose.yml` 与 `config-validate` 服务共同消费 v1 contract；使 bootstrap、初始化服务和
  server 依赖该 gate 成功。
- 验收：缺服务、环境、挂载、端口、label、secret 或 runtime 参数均有可定位 finding；gate 失败时没有 migration 或
  HTTP 服务。

## Phase 3: CI、Upgrade Guidance 与回归覆盖

- 在 CI 固化 `Build -> Config Validation -> Migration Test -> Unit Test -> Release`，并使用官方示例环境和 Compose
  模板执行独立验证。
- 为新增、废弃、删除和重命名配置提供稳定 patch 建议；补齐 Schema fixture、CLI 输出、Compose 与启动短路回归测试。
- 发布 operator 升级说明，明确 Schema version、手动 patch 流程和不写入配置文件的边界。
- 验收：release 前可检测官方模板 drift；敏感信息不出现在文本、JSON、patch、日志或 CI artifact。

## Future: Explicit Migration Command

- 仅在单独 ADR 批准后评估 `graft config migrate --write`：默认 dry-run，要求备份、原子替换、权限保留、显式确认和
  审计证据。
- 不把自动写入扩展到 Docker Secret、外部 Secret Manager 或任意用户 Compose 项目；这些边界需要各自的 authority
  与安全设计。
