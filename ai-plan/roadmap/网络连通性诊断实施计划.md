# 网络连通性诊断实施计划

## Status

Active three-phase cross-boundary delivery. Diagnostics remain target-addressed, and all later work consumes the
Phase 1 connectivity authority rather than extending the legacy HTTP-only path.

## Delivery Order

1. **Registry and Probe core**
   - Establish `ConnectivityTargetDescriptor`, typed capabilities, extensible probe kinds, versioned sanitized
     `ConnectivityReport`, and Network registry snapshots.
   - Adapt the Platform Update target through the new contract while retaining the existing HTTP boundary only as a
     migration adapter.
   - Publish the domain design and ADR. No persistence, API, route, RBAC, migration, or web changes occur here.
2. **Persistence, APIs, and security boundary**
   - Replace the legacy diagnostic history model with target/check/report persistence, bounded retention, and
     structured sanitized probe storage.
   - Add target/latest/batch/report/history/trace/export APIs, route explanation resolution, target management, SSRF
     validation, concurrency/timeouts, RBAC, Exit-IP disclosure audit, OpenAPI, and generated contracts.
   - Ensure reports remain target-addressed and do not introduce a compatibility dual-write path.
3. **Shared store, web experience, and integration**
   - Implement the Network ConnectivityStore, aggregate health header, compact batch list, target diagnostics route,
     capability-driven cards, history selection, auto-refresh, and TDesign/i18n states.
   - Validate full server/web contract flow and assess scheduled health, notification, protocol adapters, and runtime
     target health as follow-up phases.

## Phase Gates

- Phase 1 acceptance: registry ordering/uniqueness, capability snapshots, report immutability, sanitized boundary,
  and Platform Update adapter tests pass.
- Phase 2 acceptance: persistence/API security, SSRF protection, retention, permission/audit behavior, and generated
  contract drift validation pass.
- Phase 3 acceptance: batch and diagnostics share one store/domain, target route remains stable across reruns/history,
  aggregate values are correct under partial failure, and both backend and web completion entrypoints pass.
